# QPT-16 — Глоссарий

> [!note] ➕ Дополнено агентом (не из курса)
> Раздел собран по открытым источникам (документация PostgreSQL, статьи) для быстрого
> повторения. Формулировки сверены с офиц. документацией; в самом курсе этих определений в явном виде нет.

### B+ дерево (B+ tree)
Сбалансированное дерево поиска, где данные хранятся в листьях, а листья связаны в список.
Индексы Postgres по умолчанию — B+ tree: дают поиск, диапазоны и сортировку за O(log n).
Пример: `CREATE INDEX ON flights(airport)`.

### Seq Scan (последовательное чтение)
Полный проход по всем страницам таблицы. Дёшево при большой доле выбираемых строк или малых таблицах.
Пример: `Seq Scan on flights (cost=0.00..2137.00 rows=1000 width=...)`.

### Index Scan / Index Only Scan
Чтение по индексу с обращением к таблице (Index Scan) либо только из индекса, если все нужные
столбцы в нём есть (Index Only Scan; требует актуальной visibility map).

### Bitmap Heap Scan / Bitmap Index Scan
Двухфазный доступ: сначала по индексу строится битовая карта страниц (Bitmap Index Scan), затем
страницы читаются в физическом порядке (Bitmap Heap Scan). Хорош для средних селективностей.

### Nested Loop (вложенный цикл)
Для каждой строки внешнего набора ищутся подходящие строки внутреннего (обычно по индексу).
Эффективен, когда внешний набор мал, а к внутреннему есть быстрый доступ.

### Hash Join (хеш-соединение)
Строит хеш-таблицу по меньшему набору и прогоняет по ней больший. Только для эквисоединений
(`=`). Если не влезает в `work_mem`, узел вытесняет батчи на диск.

### Merge Join (соединение слиянием)
Оба входа отсортированы по ключу, далее одновременный проход. Дешёв, если сортировка уже есть
(например, из индекса) или результат всё равно нужен отсортированным.

### work_mem
Память на одну операцию (сортировка, хеш-таблица) до сброса на диск. Не глобальный лимит:
несколько узлов плана могут использовать её одновременно.

### shared_buffers
Кэш страниц в общей памяти сервера (типовое значение ≈ 25% RAM). Сглаживает разницу между
логическим и физическим вводом-выводом.

### Планировщик, стоимость и селективность
Планировщик выбирает план по стоимостной модели (условные единицы ≈ стоимость страничного
чтения). Селективность — доля строк, проходящих условие; от неё зависит выбор метода доступа и соединения.

### Статистика (ANALYZE, MCV, гистограмма)
`ANALYZE` собирает `pg_statistic`: наиболее частые значения (MCV), частоты, гистограммы и
корреляции. По ней оценивается селективность — неверные/устаревшие оценки дают плохие планы.

### EXPLAIN (ANALYZE, BUFFERS)
Показывает план и (с ANALYZE) фактическое выполнение: реальные строки, время, чтения из кэша (`BUFFERS`).
Ключ к диагностике: сравнение оценок `rows=` с фактом `actual rows=`.

### Материализация (CTE, materialized view)
CTE выполняет подзапрос один раз и кэширует результат; в PG12+ неявно материализуется только при
необходимости (можно форсировать `MATERIALIZED`). Materialized view хранит результат запроса на диске и обновляется через `REFRESH`.

### Параллельный запрос
План разбивается на воркеров (`Parallel Seq Scan`, `Parallel Hash Join`, gather-узел). Управляется
`max_parallel_workers_per_gather`, порогами и стоимостью; помогает на больших объёмах при свободных ресурсах.

**Что сверяли:** значения GUC по умолчанию, формулы оценки параллелизма, имена классов операторов (GiST/SP‑GiST/BRIN/GIN), размеры (страница 8 КБ, зона BRIN, сегмент), методы доступа и стоимости планировщика.

**Расхождения и правки:**
- SP‑GiST: для типа `point` дефолтный класс операторов — **`quad_point_ops`** (дерево квадрантов), а не `point_ops`. Исправлено в уроке 06.
- `cursor_tuple_fraction`: по умолчанию **0.1** (первые 10%) — в уроках 03 и 17 указано верно.
- Проверены и подтверждены: `work_mem=4MB`, `shared_buffers=128MB`, `maintenance_work_mem=64MB`, `effective_cache_size=4GB`, `hash_mem_multiplier=2`, `random_page_cost=4.0` (под HDD), `default_statistics_target=100`, `join_collapse_limit=8`, `max_worker_processes=8`, `min_parallel_table_scan_size=8MB`, `parallel_leader_participation=on`, BRIN `pages_per_range=128`.
